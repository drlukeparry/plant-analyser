# ROADMAP3 — Set/graph diffusion: DDIM + Transformer denoiser for cell infill

## Relationship to ROADMAP2

ROADMAP2's R2 built an **autoregressive/masked-infill GNN** (`infill_model.py`, 3× GATConv) that predicts one node's attributes at a time from real, already-known topology. It works, modestly, but never touches diffusion and depends on topology being given rather than generated.

This roadmap tests a different mechanism for the same target (see ROADMAP2's "Final target specification" — boundary + size gradient + center/direction field in, full cell tessellation out): **run DDIM directly on the set of cells**, denoising all of them together via a Transformer, instead of growing them one at a time via a GNN or rasterizing them as pixels (Phase 5/6's FieldUNet). Not a replacement for R2 — a third point of comparison alongside R2 (GNN growth) and Phase 6 (pixel DDIM).

Key framing points from the request this roadmap is built against:
- **The denoiser does not produce an image, a patch, or anything upscaling-shaped.** Its output is a list of cells (attribute vectors). Rendering that list into actual polygon geometry is Phase R3's job (Voronoi/Laguerre from centroids + sizes) — a separate, deterministic downstream step, same separation ROADMAP2 already committed to.
- **Denoiser architecture is a Transformer with self-attention, not a UNet.** A cell tessellation is an *unordered set* of cells — attention over a token set is the natural inductive bias (permutation-equivariant, no arbitrary node ordering or fixed adjacency to bake in), unlike a GNN (needs edges up front) or a patch UNet (needs a pixel grid).
- **Conditioning is spatial and per-cell, ControlNet-style**: boundary shape, size gradient, direction/alignment field are all sampled *at each cell's position* and fed in per-token, not as one global vector — the graph-space analogue of ControlNet feeding a spatial conditioning map into a UNet's residual blocks.

## Why diffusion over autoregressive growth here

- **Global consistency in one shot.** R2's GNN grows cells sequentially from local neighborhood context only — nothing enforces a long-range consistent layout except however far growth has propagated. A set-level DDIM denoises the whole token set jointly at every step; each cell's final attributes are informed by attention over the *entire* set (and the full conditioning field) from the start, not just already-placed neighbors. This is the same "no seams by construction" argument ROADMAP2 makes for graph generation in general, pushed one level further: no growth-order artifacts either.
- **Matches the existing pipeline's mechanism.** Phase 5/6 already validated the DDIM/`diffusers.DDIMScheduler` training-and-sampling loop on this exact codebase and dataset. Reusing the scheduler, just swapping the denoiser's input/output tensor shape from "pixel grid" to "token set," is a small, well-precedented change — lower-risk than inventing a new generative mechanism from scratch.
- **Cardinality is still awkward either way.** Diffusion doesn't remove R2's hardest open problem (how many cells, when to stop) — see Open Questions below. This roadmap treats that as a shared unsolved problem, not a reason to prefer one mechanism over the other; the comparison itself is the point.

## Representation

- Each cell = one token: **position** `(radial_distance_norm, angular_position)` or raw `(x, y)` in tissue-normalized coordinates (Phase 3's existing normalization) concatenated with the **13 existing node attributes** (`area_norm`, `elongation`, `orientation`, `solidity`, etc. — same feature set R1/R2 already use). No image channels anywhere.
- **Adjacency is not part of the generative target.** Dropped entirely, same call ROADMAP2's R3 already made for the GNN path: edges are recovered deterministically from generated positions via Voronoi/Delaunay once geometry is rendered. This sidesteps R2's still-deferred "attachment/topology prediction" problem rather than solving it — worth stating plainly, not implicitly assuming diffusion solves it for free.
- **Fixed-cardinality token set (N_max) with a padding mask**, standard practice for point-set/set diffusion. Real subgraphs (reusing Phase 3's k-hop sampler) supply between a few and N_max real cells; pad with a learned pad token and an explicit active/inactive flag per token, loss computed only over active tokens. Variable cell-count generation (arbitrary region, arbitrary target density) is handled at the *sampling* stage, not by training a variable-length model — see D4.

## Denoiser architecture (D2)

DiT-style (Diffusion Transformer) design, adapted for a set instead of a pixel grid:

- **Backbone:** standard Transformer encoder, full self-attention across all N_max tokens (no causal mask — this is a set, not a sequence).
- **Per-token input:** noisy attribute vector (13-dim) + the token's `(x, y)` position (positions are conditioning, not denoised — see D4 for why) + sinusoidal embedding of `(x, y)` + diffusion-timestep embedding, combined via AdaLN-Zero (DiT's conditioning mechanism) rather than concatenation, so timestep conditioning modulates every block cleanly.
- **ControlNet-style spatial conditioning, per token:**
  - `size_gradient_target` sampled at `(x, y)` from the input size field (reuses `control_fields.py`'s extraction logic, applied to a synthetic or transplanted-real field at inference time).
  - `alignment_flow_angle` / `alignment_flow_coherence` sampled at `(x, y)` (same source).
  - signed distance from `(x, y)` to the input boundary polygon — tells the model "near the edge, shrink/orient tangentially" vs. "interior."
  - These are concatenated into a per-token conditioning vector and injected the same way the timestep embedding is (AdaLN-Zero), zero-initialized on the conditioning pathway specifically (ControlNet's own trick) so the base denoiser can't be destabilized early in training before the conditioning signal is useful.
- **Scheduler:** reuse `diffusers.DDIMScheduler` unchanged — only the noise-prediction network's input/output shape changes, from Phase 5/6's `[B, 4, H, W]` field to `[B, N_max, 13]` (+ mask).
- **Start small**, per this repo's established pattern (Phase 5 started at ~1M params before Phase 6 scaled to 2.1M) — a first prototype should prove the loop end-to-end on a small model/short run before any scale-up.

This is proof-of-loop only, per the plan's own "start small, short run, prove the loop before scaling" bar — not evidence of generation quality.
- Implement the DiT-style architecture above (`src/roadmap3/denoiser.py`, `src/roadmap3/train.py`), reusing `diffusers.DDIMScheduler`.
- Loss: standard eps-prediction MSE, masked to active tokens only. Positions are conditioning inputs, not part of the loss target (see D4).

### D3 — Unconditional / self-conditioned sanity check
**Status: done for a first real training run (3000 steps, 1.26M params) — control-following works, matching R2's GNN baseline.** `src/roadmap3/sample.py` — DDIM reverse sampling conditioned on a real subgraph's own extracted control fields, pooled feature-distribution comparison (`area_norm`/`elongation`/`orientation`, same 0.5-std effect-size bar Phase 6 used) plus the control-following correlation check R2 introduced (`corr(size_gradient_target, generated equivalent_diameter_norm)`).

**First full-budget run (3000 steps, `hidden_dim=128`, `n_layers=4`, loss 1.00 → 0.16) initially showed control-following correlation ≈0 (-0.007)** — investigated rather than accepted, since R2's GNN got 0.466 on the same check. Root cause: `size_gradient_target` (mean 0.0058, std 0.0022) was fed into `ctrl_proj` **unstandardized**, while it's added directly to `input_proj(x)` where `x` is standardized to unit variance (see `denoiser.py`) — the control signal was ~500x smaller in scale than what it was summed with, numerically drowned out regardless of training budget. This is a straightforward scaling bug, not evidence against the conditioning mechanism.

**Fixed** (`train.py`/`sample.py`: `ctrl` now standardized the same way `x` is, scaler saved/reloaded alongside the model) **and retrained from scratch, same budget:**

| check | before fix | after fix | R2 (GNN) reference |
|---|---|---|---|
| `corr(size_gradient_target, generated equivalent_diameter_norm)` | -0.007 | **0.458** | 0.466 |
| `area_norm` effect size | 0.476 | 0.158 | — |
| `elongation` effect size | 0.046 | 0.002 | — |
| `orientation` effect size | 0.061 | 0.431 (within 0.5 bar, closest to it) | — |

Control-following now lands within noise of R2's GNN result on the same metric, at a comparable first-pass training budget — a real, positive signal that the Transformer denoiser's per-token control-field conditioning is being used, not just tolerated. `orientation`'s effect size is the one distributional check closest to the 0.5-std bar and worth watching on any longer run, but not yet a failure.

**Not yet done:** a longer/larger training run (this is still a first-pass budget, matching Phase 3/5's original single-run length, not a scaled-up run); a real train/held-out-image split (same caveat as R1/R2 — this is in-sample); D4's position-handling decision (this run diffuses position dims — `radial_distance_norm`/`angular_position` — along with everything else, it does not yet test the fixed-position/blue-noise-seeded variant).
- Before testing arbitrary novel conditioning, first confirm the model can regenerate plausible *real-distribution* cell sets when conditioned on a real image's own extracted control fields (i.e. reproduce roughly what R2/Phase 6 already validate against) — same "does this even work" gate every prior phase used before testing generalization.
- Validate with ROADMAP2's existing bar: pooled feature-distribution comparison (area/elongation/orientation) against real cells, effect-size threshold consistent with Phase 6's 0.5-std bar, plus the control-following check R2 introduced (does generated size track the requested gradient — correlation, not just distributional match).

### D3.5 — Geometry rendering (ROADMAP2's R3, wired to this checkpoint)
**Status: fast-preview tier implemented and wired to the trained checkpoint.** `src/roadmap3/geometry.py` implements a real weighted (Laguerre/power-diagram) Voronoi tessellation directly via Sutherland-Hodgman half-plane clipping (numpy only, no new dependency) rather than pulling in a power-diagram library — each cell's clip region is `{p : |p-c_i|^2 - w_i <= |p-c_j|^2 - w_j ∀j}`, with `w_i = (equivalent_diameter_norm_i / 2)^2`, so a cell's *own* target size actually determines its rendered polygon's size, not just its centroid's spacing (the stated reason ROADMAP2 R3 prefers weighted over plain Voronoi). `src/roadmap3/render.py` renders real vs. generated cell sets side by side (`outputs/roadmap3/d3_geometry_render.png`).

**A real methodological finding, not just a rendering script:** cells whose polygon touches the tessellation's arbitrary clip-box edge have to be excluded from any area-based comparison — their extent is a function of the clip box, not the site's own weight (a genuine property of power diagrams: an isolated or boundary site's territory is unbounded unless clipped). `geometry.is_boundary_cell` flags these; they're dropped from both the plotted color scale and any quantitative check.

**Quantitative check — `corr(a cell's own diameter, its rendered polygon area)`, interior cells only, 5 real/generated subgraph pairs:** real = 0.177 (range -0.32 to 0.75 across the 5 samples — noisy, small-N), generated = 0.282. The two are comparable, and generated is not obviously worse. This matters because it means the low absolute correlation is **not evidence the denoiser's sizes are wrong** — a power-diagram cell's area is a function of local neighbor spacing/density as much as its own weight, so even real cells (from genuinely correct positions+sizes) don't show a strong self-size-to-rendered-area correlation. The earlier, more direct check (D3: `corr(requested size_gradient_target, generated equivalent_diameter_norm) = 0.458`) remains the right metric for "is the model generating the right sizes" — this geometry-level check is instead validating the *renderer*, and the honest reading is that it passes a sanity check (generated ≈ real, both weak) rather than either confirming or refuting anything about the denoiser.

**Visual read:** generated tessellations are qualitatively plausible — irregular, varied-size polygons, no overlaps or degenerate collapse — and in several examples visibly denser/better-packed than the corresponding real sample. Some real *and* generated samples both show a thin, elongated (near-1D) cluster shape rather than a compact blob; plausibly reflects genuine plant-tissue ray structure (radially-aligned parenchyma files) surfacing in the k-hop sampling, not a rendering bug — not confirmed against reference anatomy, worth checking if this recurs.

**Not yet done:** the higher-fidelity relaxation tier (out of scope per the plan, only pursued if this fast-preview tier proved unconvincing — it didn't, so no reason yet to invest there); comparing rendered polygon shape features (elongation, solidity — not just area) against real cell wall shapes, the comparison ROADMAP2 R3 originally specified; D5's arbitrary-boundary/synthetic-control-field test, which is the actual point of "infill generation" and hasn't been attempted (this render only regenerates within a real subgraph's own footprint).

### D4 — Position handling: the actual open design decision
Diffusion needs *some* token position to sample the spatial conditioning fields at, but position is also plausibly something the model should generate, not receive as fixed input. Two variants to build and compare, cheapest first:

- **D4a (build first): positions fixed, only attributes diffused.** Seed token positions via a blue-noise/Poisson-disk point process over the boundary polygon, local intensity set from the size-gradient field (denser where target cell size is smaller) — a deterministic, non-learned step, same spirit as R3's "geometry is a deterministic rendering step, not something the model learns implicitly." The Transformer then only denoises the 13 attributes at each fixed, pre-placed position. Simpler, avoids re-sampling spatial conditioning mid-trajectory, and directly reuses this repo's existing "decouple placement from content" philosophy (ROADMAP2 already decouples geometry-rendering from graph-generation this same way).
- **D4b (only if D4a's ceiling is reached): positions are part of the diffused vector too.** Requires re-sampling the control fields at the *current noisy position estimate* at every DDIM step (literal ControlNet-style re-conditioning per denoising step, since the conditioning signal is itself position-dependent) — meaningfully more complex, and only worth building if D4a demonstrably can't produce good layouts because it's too dependent on the blue-noise seed's quality.

**D4a status: implemented, and a real negative result found.** `synthetic.py` seeds cell positions via dart-throwing blue noise (density set by a target-size field, calibrated to real per-patch cell density — see its docstring), `inpaint.py` implements RePaint-style position pinning (Lugmayr et al.: the known region is re-noised to the current step's noise level and pasted into `x` before every model call, not overwritten once) so the trained joint denoiser can be reused unmodified with positions held fixed.

**It works mechanically (runs, converges, produces a plausible-looking tessellation) but control-following degrades sharply under pinning, even for real, in-distribution positions:** pinning to 5 REAL subgraphs' own real positions + real ctrl (i.e. nothing synthetic, nothing out-of-distribution) dropped `corr(size_gradient_target, generated diameter)` from D3's 0.458 (free joint generation) to a mean of **0.167** (range 0.04–0.32 across the 5). This isolates the cause: **the degradation is the position-pinning mechanism itself, not synthetic/out-of-distribution control values.** The model learned to generate position and attributes jointly (attention over other tokens' *evolving* positions is plausibly serving as an implicit spatial signal the model uses alongside `ctrl` to decide sizes) — forcibly overwriting position with an externally supplied value at every step breaks that internal coupling, RePaint's re-noising trick notwithstanding.

**Practical implication:** D4a as specified (train jointly, pin positions post-hoc at inference) is the wrong way to decouple position from attributes for this architecture. The fix is a training-time change, not a sampling-time one — either (a) train a variant where position is genuinely a *conditioning input* from the start (concatenated into the per-token conditioning the same way `ctrl` already is, never part of the diffusion target), so the model never has to reconcile its own generated positions with externally pinned ones, or (b) revisit D4b (diffuse position too, re-sample `ctrl` at the evolving position each step) despite its added complexity, since D4a's simplicity turned out to not actually hold up. **Not yet done** — this is a finding, not a fix; retraining a position-as-conditioning variant is the concrete next step before trusting any infill-generation result built on this checkpoint.

### D5 — Whole-region infill + comparison against R2 and Phase 6
**Status: first pass run, inherits D4a's finding above -- read its numbers accordingly.** `synthetic_demo.py` builds a synthetic circular boundary (radius 0.15, patch-scale, not full-structure), a size gradient deliberately steeper than the real dataset's own range (diam 0.010 at center vs. 0.003 at edge, vs. real mean+/-std of 0.0059+/-0.0042), and a tangential alignment-flow field -- none of it lifted from a real image, the actual "novel control input" test this roadmap targets. Ran with 100 seeded cells.

**Result: corr(requested synthetic size field, generated diameter) = 0.049** -- weak, but consistent with (not much worse than) D4a's 0.167 real-position-pinned baseline above once the position-pinning mechanism's own cost is accounted for, rather than a separate, larger generalization failure. **The rendered tessellation visually shows a plausible-looking radial size gradient** (`outputs/roadmap3/d5_synthetic_infill.png`) -- but this is very likely substantially an artifact of the blue-noise seeding density itself (cells were already spaced denser/sparser according to the same target-size field before the model ever ran), not strong evidence the model's generated attributes are genuinely tracking the field in this setting. The direct attribute-level correlation (0.049) is the number to trust, not the visual impression.

**Conclusion for this pass:** D5 is blocked on D4a's finding, not on anything specific to synthetic boundaries/gradients. Re-running this exact test after a position-as-conditioning retrain (D4a's proposed fix) is the right next step, rather than iterating further on the synthetic-boundary setup itself.

### Position-as-conditioning retrain: fixes D4a's finding partially, and surfaces a distinct, real generalization gap
**Status: implemented, trained (same 3000-step budget), and re-tested on both the real in-distribution and synthetic settings above.** `train_poscond.py` moves position (`radial_distance_norm`, `angular_position`) entirely out of the diffusion target and into the per-token conditioning vector (concatenated with the existing 4-dim control field, `ctrl_dim` 4→6, `attr_dim` 13→11) — `SetDenoiser` needed no architecture change, only a different slicing of the same training batches. `sample_poscond.py` samples it directly (no RePaint needed — position is a plain input the model was actually trained on). Loss curve: 1.00 → ~0.10-0.15, comparable to the original run.

**All four numbers, same `corr(size_gradient_target, generated diameter)` metric throughout:**

| setting | free joint generation (original) | position-as-conditioning (this retrain) |
|---|---|---|
| real, in-distribution (pooled, 59 subgraphs) | 0.458 | **0.364** |
| RePaint-pinned real (5 subgraphs, for comparison) | — (n/a, no pinning in this variant) | 0.167 *(pre-retrain baseline)* |
| synthetic boundary + novel gradient (D5) | — (n/a) | **0.083** *(RePaint version: 0.049)* |

Reading this honestly, in two parts:

1. **The retrain substantially fixes D4a's actual finding.** In-distribution control-following recovered from the RePaint baseline's 0.167 to 0.364 — real progress, confirming the diagnosis was right: pinning a jointly-trained model's positions was the problem, not something inherent to decoupling position from attributes. It doesn't fully close the gap to the free-joint ceiling (0.458) — plausibly because joint generation gets an extra, correlated degree of freedom (the model can adjust *both* position and size together to satisfy a control target, where the position-conditioned model only has size left to work with) — but the fix clearly helped, not just changed the failure mode.
2. **A second, distinct generalization gap remains on the synthetic boundary (0.083), not explained by pinning.** No RePaint is used in this configuration at all, so this number reflects the model's actual behavior on genuinely novel input. The rendered tessellation still looks visually plausible (`d5_synthetic_infill_poscond.png`) and is nearly identical in layout to the earlier RePaint-based render (same blue-noise seed reused, not a coincidence) — reinforcing D5's original caveat that the visual impression is driven substantially by the deterministic position-seeding density, not the model's generated sizes. The likely cause here is not the control-field *values* (0.010/0.003 diam is not wildly outside the real range of 0.0059±0.0042) but the **point-cloud's spatial shape**: blue-noise seeding produces a roughly uniform-density filled disk, while real k-hop training subgraphs (per D3.5's render) often look like thin, elongated chains (plausibly tissue-ray structure) rather than compact uniform blobs — a distribution shift in local neighborhood *geometry*, not just in control-field magnitude, that this pass didn't anticipate or test for separately.

**Practical conclusion:** position-as-conditioning is the right fix for D4a's original finding and should be the basis for any further work on this checkpoint. But it is not sufficient on its own to make novel-boundary infill work well yet — the next real question is whether the synthetic seeding process needs to better match real local point-cloud statistics (not just density-by-target-size, but also shape/elongation), or whether the model needs training exposure to non-real (e.g. Poisson-disk) position layouts specifically, rather than only ever training on real k-hop subgraph geometry. Neither has been tried.

### Attempted DO_0000 subsection replication — a visual match that doesn't mean what it looks like
`replicate_do0000.py`: real positions + DO_0000's own real control fields (not synthetic, not pooled across other images) for a 124-cell subsection, generated with the position-conditioned model. Rendered side by side against the real subsection (`outputs/roadmap3/do0000_replication.png`).

**The rendered images look strikingly similar** — same large cell in the same spot, same green cells, near-identical overall layout. **This is misleading, and worth stating plainly rather than reporting as a success.** Since both panels use the identical real positions, the tessellation geometry (and the polygon area used for coloring) is dominated by that shared position layout regardless of what the model actually generated — per D3.5's own earlier finding that rendered area depends on neighbor spacing more than a cell's own attribute. Checking directly (`corr(real cell's own attribute, generated cell's own attribute)`, per feature, matched cell-for-cell) gives **0.07 (area_norm), 0.06 (diameter), 0.04 (elongation), -0.05 (orientation), -0.02 (solidity), 0.06 (eccentricity)** — essentially zero. The model is not reconstructing DO_0000's actual individual cells.

This is not necessarily a failure of the model, but a mismatch between what this pass tested and what "replicate" implies. `ctrl` only ever encodes a *smoothed, local-neighborhood* trend (`control_fields.py`'s k=8 leave-one-out mean) — a genuinely stochastic DDIM sample conditioned on that smoothed trend has no reason to reproduce any specific real cell's own particular value, only to be a plausible draw consistent with the local trend (which is what D3's pooled/distributional checks actually measure, and did validate). **"Replicate a real specimen's actual cells" is a different, harder task than this checkpoint was built or validated for** — closer to R1's decoder-reconstruction problem (given the real cell, recover it) than to this roadmap's generation problem (given a control trend, produce a plausible new cell). Attempting true per-cell reconstruction would need the real cell's own identity encoded into the conditioning somehow (e.g. a GVAE-style per-node latent, not just the smoothed neighborhood field) — out of scope for what's been built here.

### Attempted whole-structure generation — all of DO_0000 (6,748 cells) in one connected DDIM pass
`full_structure.py`: real positions + DO_0000's own real control fields for its **entire** cell set (not a patch, not tiled) — the actual point of doing this in graph/token space at all: one genuinely connected self-attention pass instead of Phase 5/6's independently-generated, stitched pixel tiles.

**Generation cost was not the bottleneck — it turned out to be a non-issue.** A single forward pass over all 6,748 tokens measured at 0.37s; the full 50-step DDIM reverse loop over the whole structure took **4.4 seconds total**. ROADMAP3's own flagged risk ("O(N²) attention cost... may be the actual bottleneck... needs measuring") turned out not to bind in practice at this scale, on this hardware. (The pure-Python power-diagram renderer, by contrast, does not scale to 6,748 sites — a small spatial crop is rendered for visual inspection only, statistics below are computed over the full generated set.)

**But quality did not survive the scale jump.** Whole-structure `corr(size_gradient_target, generated diameter) = 0.024` — essentially zero, far below even the synthetic-boundary result (0.083) and nowhere near the patch-scale in-distribution result (0.364). `area_norm`'s distribution effect size hit **0.530**, the first time any effect size in this project has crossed Phase 6's 0.5-std bar. `elongation` (0.020) and `orientation` (0.377) stayed within bar.

**Visual confirmation** (`full_structure_scatter.py`, `outputs/roadmap3/do0000_full_structure_scatter.png` — a fast O(N) scatter over all 6,748 positions, marker size/color = diameter, since the power-diagram renderer doesn't scale here): real DO_0000 shows clear, varied cell sizes (dark small cells through bright yellow large ones); the generated structure has collapsed to near-uniform small (dark) cells across the entire structure. The model isn't subtly mis-tracking the size field at this scale, it's barely using its size range at all — visually obvious, not just a weak correlation number.

**The failure is worse for the ORIGINAL free-joint model** (`free_joint_full_structure.py`, before the position-as-conditioning fix), which generates its own positions from noise rather than taking them as real input. Run at DO_0000's full scale for the first time (previously only ever tested at ≤300-token patch scale): real `radial_distance_norm` spans 0.014–1.116 (the full disk); the free-joint model's generated positions collapsed to **0.644–0.847**, a narrow band — visually (`outputs/roadmap3/do0000_positions_vs_generated.png`) this is not a distorted stem shape, it's almost the entire 6,748-token output crammed into one small blob, axes ranges differing by ~20x between the real and generated panels. This is a more severe failure than the position-conditioned model's (which at least keeps real, correctly-shaped positions and only mis-generates attributes) — confirms position generation is *harder* to length-generalize than attribute generation, consistent with position being the higher-dimensional, more structurally entangled part of what the joint model has to get right.

**Not a surprise given what the model was actually trained on:** `n_max=64` was the training batch size, and even the largest patch tested anywhere in this roadmap (the 124-cell DO_0000 subsection above) is 34x smaller than 6,748. Full self-attention has no positional/length restriction architecturally (per denoiser.py's own docstring), but nothing here suggests the *learned weights* generalize to a sequence this much longer than training — attention patterns, learned implicitly from ≤200-token examples, have no reason to remain sensible at 6,748 tokens, and this result confirms they don't. This is a length-generalization failure, a distinct (and more severe) problem from D5's spatial-shape generalization gap — worth keeping separate when deciding what to fix next, since the fix for one (e.g. training on more real-shaped point clouds) doesn't obviously address the other (training would need genuinely large real subgraphs, not just more of the same ≤200-node patches).

### Tested alternative to D6: just train on longer sequences
Before committing to D6's representation change, tested the simpler question directly: does training the *existing* architecture on much longer sequences close the length-generalization gap, rather than redesigning placement entirely?

**Real image scale, checked first:** the 213 real images range from 5,446 to **90,309** cells (median 18,894) — training on literal whole images is impractical (O(N²) attention at 90k tokens is ~180x the cost measured at 6,748; and only 213 unique whole-image examples would be a severe overfitting risk vs. the effectively-unlimited augmented crops random subgraph sampling provides). Practical middle ground: much larger random crops (2,000 tokens via 25-hop subgraphs, calibrated empirically — hop count grows roughly quadratically with node count for this 2D tissue structure) instead of the previous 64-token training scale, keeping the crop-sampling augmentation benefit while cutting `DO_0000`'s length-extrapolation factor from 34x down to ~3.4x.

**Retrained from scratch** (`train_poscond.py`, now parameterized for `num_hops`/`max_nodes`, `n_max=2000`, batch_size=4, same 3000-step budget, saved under a separate `_large` suffix): loss curve comparable (1.00 → ~0.05-0.27, noisier than the small-context run but still converging).

**Result: real but partial improvement — confirms the diagnosis, doesn't solve it.**

| metric (DO_0000 full scale, n=6,748) | n_max=64 (before) | n_max=2000 (this test) |
|---|---|---|
| whole-structure control-following | 0.024 | **0.102** (4.3x) |
| `area_norm` effect size | 0.530 | 0.623 (worse) |
| `elongation` effect size | 0.020 | 0.323 (worse) |
| `orientation` effect size | 0.377 | 0.245 (better) |

Control-following genuinely improved (4x), confirming training-length exposure is a real, causal factor in the length-generalization failure, not something else entirely. But it's a mixed result elsewhere (two of three distribution checks got worse) and the visual output (`outputs/roadmap3/do0000_full_structure_scatter_large.png`) still shows the same qualitative failure as before — collapsed to near-uniform small cells across the structure, not tracking real size variation. Nowhere near patch-scale quality (0.364).

**A per-cell scatter (`do0000_full_structure_corr_scatter.png`, requested vs. generated, one point per real cell) surfaced a real, session-spanning implementation detail worth flagging plainly:** `diffusers.DDIMScheduler`'s default is `clip_sample=True, clip_sample_range=1.0` — a hard ceiling visible in the scatter as a dense flat band at generated diameter ≈ 0.0102. This scheduler default is designed for image diffusion, where pixel values are normalized to [-1, 1]; this project's data is z-scored (zero mean, unit variance) instead, so the clip silently caps every generated attribute at ±1 standardized unit during every reverse-sampling call across this entire roadmap (`sample.py`, `sample_poscond.py`, `inpaint.py` all construct `DDIMScheduler` with the default). **Investigated rather than assumed:** re-ran this same test with `clip_sample=False` — correlation got *worse* (0.102 → 0.005), and the generated range exploded past anything physically real (-0.060 to 0.153, vs. real 0.005–0.028; `do0000_full_structure_corr_scatter_noclip.png`). So the clip is not the cause of the length-generalization failure — at this far-out-of-distribution scale the model's raw output is simply unstable, and the default clip is incidentally providing free regularization, not hiding a fixable bug. The length-generalization diagnosis above stands. Worth revisiting `clip_sample_range` (e.g. setting it to something matched to the actual standardized data range, like ±4-5, rather than ±1 or disabled entirely) as a real, cheap tuning knob for a future pass — untested here, since the two extremes tested (default 1.0 vs. off) don't establish whether an intermediate value helps.

**Conclusion:** pushing training sequence length up helps incrementally but doesn't cheaply solve the problem — extrapolating from this result, closing the remaining ~3.4x gap (let alone the ~13x gap to the median real image, 18,894 cells) by continuing to scale `n_max` would need substantially more compute and still isn't guaranteed to fully close, since the relationship looks like partial mitigation, not a clean fix. This is the concrete evidence for preferring D6's scale-invariant approach (which removes the length dependency rather than trying to outrun it) over simply continuing to scale training length — though "just train longer" remains the cheaper lever to keep pulling if D6 proves harder to build than expected.

### D6 — Placement as a separate, scale-invariant problem (density field + point process)
**Status: first prototype implemented and run — infrastructure works end-to-end, two real limitations found in the fast tier, neither fatal.** Motivated directly by the whole-structure findings above: every failure traced back to *placement*, not attribute quality — the free-joint model's self-generated positions collapsed catastrophically (D4/whole-structure section), and both attempted placement fixes so far (RePaint pinning, position-as-conditioning) only ever *consume* positions (real or D5's hand-specified blue noise), neither actually learns to place cells well when no reference positions exist. This phase reframes placement as its own, deliberately scale-invariant sub-problem, explicitly deferring size/orientation/shape generation to whatever this phase's output feeds into downstream.

**Core diagnosis carried in from D4/D5/whole-structure:** a single global full-attention pass over a token count fixed by training does not generalize to arbitrary N — this is a token-length representation problem, not a training-budget or data-quantity problem, so the fix needs to change *how placement is represented*, not just retrain longer.

**Proposed approach:**
1. **Learn a local target-density/spacing field, not individual point coordinates.** Reuses this repo's existing rasterized field representation (Phase 4/5's `field.py` channels) rather than a fixed-N token set — a raster/CNN-style model is architecturally scale-invariant (tiles to any output size, unlike attention over a token count fixed at training time), which directly targets the length-generalization failure at its root instead of working around it. Trained on real per-image local cell density (extend `control_fields.py`'s existing k=8 leave-one-out smoothing to a density estimate — e.g. inverse mean nearest-neighbor spacing — the same way it already computes the size-gradient field), conditioned on the boundary + existing control-field inputs.
2. **Sample actual point positions from the learned density field via a real spatial point process**, not D5's hand-specified dart-throwing blue noise. Two tiers, cheapest first (mirroring R3's own fast-preview-first precedent):
   - **Fast tier:** density-weighted Poisson-disk sampling — what D5 already approximates, but driven by the *learned* density field instead of a hand-specified one. Immediate, useful for iteration.
   - **Higher-fidelity tier, only if the fast tier's packing statistics don't match real:** a Gibbs/pairwise-interaction point process fit to real cell-to-cell nearest-neighbor distance statistics — classical spatial-statistics tooling, real engineering to wire up (a point-process library, or a simple MCMC/simulated-annealing fit against a real empirical nearest-neighbor-distance distribution) but not something this roadmap needs to invent from scratch.
3. **Validate placement on its own terms, separately from attribute quality** — a new validation axis this roadmap hasn't needed before, since every prior D3/D5 check either consumed real positions directly or measured attribute quality, never placement quality alone. Compare generated point-set statistics (nearest-neighbor distance distribution, local density vs. requested target, a clustering statistic such as Ripley's K) against real DO_0000/EH/VM point sets.
4. **Only after placement validates on its own** should it be reconnected to the existing attribute-generation pipeline — feed the learned/sampled positions into the position-conditioned `SetDenoiser` (D4a's retrain, already validated at patch scale: 0.364 pooled control-following) as the position-conditioning input, exactly as D4a already does for real or blue-noise-seeded positions. Nothing about the attribute-generation side needs to change for this phase.

**Explicit scope boundary:** this phase deliberately does not attempt to also fix size/orientation/shape generation at whole-structure scale — that failure (0.024 whole-structure control-following) is left as a separate, later problem, on the working assumption that once placement is right, the existing patch-validated attribute model can plausibly be applied locally/windowed across a correctly-placed whole structure without its own architecture change. That assumption is untested and would need its own phase to confirm, not something D6 should be asked to prove as a side effect.

**Relationship to the alternative already discussed (local/windowed attention + autoregressive growth):** remains a legitimate fallback if D6's higher-fidelity point-process tier proves unconvincing, but isn't pursued here since it reintroduces ROADMAP2 R2-style growth-order/stopping-rule complexity this roadmap was originally motivated to avoid (see "Why diffusion over autoregressive growth here" at the top of this document).

**Open questions before committing significant time:**
- Does a real, learned density field differ meaningfully from D5's hand-specified one in a way that matters for placement quality — or was D5's placement-adjacent visual plausibility (the tessellation "looking" gradient-consistent, per D3.5/D5's own caveat about that impression being unreliable) already about as good as it gets, with the real gap entirely on the attribute side? Worth a quick real-vs-hand-specified density field comparison before investing in point-process fitting.
- Is Poisson-disk (fast tier) sufficient, or does real cell packing show clustering/regularity statistics a simple minimum-distance rejection process structurally can't reproduce? Needs measuring (nearest-neighbor distance distribution comparison against real), not assumed either way.
- How should this phase's output be validated against the free-joint/position-conditioned models' own position behavior from D4/D5/whole-structure, to confirm a genuine improvement rather than a different-looking failure mode?

**First prototype, what was built (`control_fields.py::local_density_field`, `d6_density_field.py`, `d6_model.py`, `d6_train.py`, `d6_validate.py`):**
- `local_density_field`: the standard k-NN density estimator (`k / (pi * r_k^2)`, leave-one-out), same style/coordinate-system as the existing size-gradient/alignment-flow fields.
- `d6_density_field.py` rasterizes real images directly from `node_df`'s existing `_norm` coordinates onto a small, fixed 48x48 grid shared across all images (not Phase4/5's native-resolution label-image rasterization, no per-image scale leak by construction) — a `boundary_mask` (silhouette proxy from k-NN distance to the real point set) and a Gaussian-smoothed `density_raster`, both new, deliberately validated visually before use (same discipline as ROADMAP2's own field validation): real density rasters showed genuine spatial structure, including a visible low-density dip at the pith center on `EH_0049`/`VM_0033`, biologically plausible and consistent with earlier findings elsewhere in this project.
- `d6_model.py`/`d6_train.py`: a small conv encoder-decoder (83.8K params, `boundary_mask` in, log-density out — `log1p` used since raw density varies ~5x between images, the same cross-image scale leak Phase 3 already found and fixed for node features), trained on all 213 images with flip/rotation augmentation (legitimate here, unlike the graph case, since a density field has real rotational/reflective symmetry). 1500 steps, loss 77 → ~0.3-0.4.

**Finding 1 — density-LEVEL prediction regresses toward a global mean; boundary shape alone doesn't determine it.** Checked in log-space directly rather than trusting the raw-space visualization (which looked like saturation but wasn't — see below): `DO_0000` real mean log-density 7.84 vs. predicted 8.87 (~2.8x overpredicted in linear space); `EH_0049` 7.86 vs. 8.57 (~2x over); `VM_0033` 9.51 vs. 8.45 (~2.9x *under*predicted) — the model converges toward one absolute density level across all three images rather than each image's own actual level, even though real density varies genuinely (`VM_0033` is ~5x denser than `DO_0000`). Consistent explanation: nothing in the model's only input (a binary silhouette) actually signals overall density level — it's not observable from boundary shape alone, so the model can't do better than an average without an additional conditioning signal (e.g. an explicit target-density scalar, the same role `size_gradient_target` already plays for the token model). This is the same "collapses toward the mean when the signal isn't in the input" failure mode observed elsewhere in this project (R1's decoder, the whole-structure attribute results) — not a new kind of problem, a familiar one in a new place.

**Finding 2 — the fast-tier point process (dart-throwing blue noise) under-fills badly at real scale, independent of the density model's own accuracy.** `d6_validate.py`'s placement check compared generated vs. real nearest-neighbor distance distributions on all three images: generated point counts fell far short of the real count even with `max_points` uncapped — `DO_0000` 5,394/6,748 (80%), `EH_0049` 4,991/8,377 (60%), `VM_0033` **4,865/43,753 (11%)**. Root cause confirmed directly, not assumed: `seed_positions_blue_noise`'s `max_candidates=20000` default — rejection-sampling acceptance rate collapses as an area fills toward its target packing density, and `VM_0033`'s real density (~5x `DO_0000`'s) needs far more than 20,000 random throws to saturate. This is exactly the limitation `synthetic.py`'s own docstring already flagged ("not a rigorous Poisson-disk implementation, no guaranteed maximal packing") — now empirically confirmed at real-image scale, and the direct, concrete case for building D6's "higher-fidelity tier" (a proper Poisson-disk algorithm, e.g. Bridson's — near-maximal packing in close to linear time, not random rejection) sooner rather than only if the fast tier "doesn't look right."

**Net assessment:** the D6 architecture itself — raster/CNN density field, scale-invariant by construction — behaves as expected: no length-generalization collapse of the kind D4/whole-structure showed, because nothing here scales with token count. Both problems found are fixable, understood, and separable: Finding 1 needs an added conditioning input (not a redesign), Finding 2 needs a better point-process algorithm (already anticipated as the "higher-fidelity tier," just needed sooner than planned). Neither is evidence against the core D6 approach — both are the kind of concrete, addressable gaps a first prototype is supposed to surface.

## Open questions / risks, stated up front

- **Cardinality is unsolved, not sidestepped.** Fixed N_max training + a separately-seeded point process (D4a) chooses *where* cells go and implicitly *how many*, but that choice is made by the non-learned blue-noise step, not learned generation — worth being honest that this roadmap doesn't solve "learn how many cells to generate," it delegates the question to a deterministic point process, same as it delegates geometry to a deterministic renderer.
- **O(N²) attention cost at scale.** Full self-attention over thousands of tokens (a real whole-structure cross-section) may be the actual bottleneck that determines whether this beats Phase 6's tiled pixel-DDIM at scale — needs measuring (D5), not assumed favorable just because it avoids per-tile seams.
- **R1's decoder finding is a warning, not directly applicable, but relevant in spirit:** R1 found the existing GVAE decoder reconstructs position well but collapses shape/size features toward the mean. This roadmap doesn't reuse that decoder, but the same failure mode (a model that's good at the spatially-smooth part of the target and bad at the intrinsically-noisy per-cell part) is worth watching for here too, especially for `eccentricity`/`solidity`-type features that R1 and R2 both struggled with.
- **No held-out image split**, same caveat as R1/R2 — all evaluation here is in-sample until a real train/test split by image is set up.

## Dependencies

No new dependencies expected — `diffusers` (`DDIMScheduler`) and `torch` are already in `pyproject.toml`. A plain `nn.TransformerEncoder` (or a small hand-rolled pre-norm attention stack, matching the "start small" precedent of Phase 5's hand-rolled UNet rather than pulling in a full DiT library) covers D2.
